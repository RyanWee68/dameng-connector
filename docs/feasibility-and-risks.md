# 大事务捕获可行性与风险记录

记录日期：2026-10-12。本记录供项目可行性与上线风险讨论使用，不代表生产验收通过。

## 正式方案

- 挖掘启动传入 STARTSCN / ENDSCN，读取条件继续使用 `SCN > startScn AND SCN <= endScn`，保留日志排序与跨轮事务缓存。
- 有积压时下一轮窗口倍增，受最大值限制；接近数据库当前位置时按最小窗口参数线性回落。默认初始 20,000、最小及缩窗步长 1,000、最大 100,000。
- 本次测试使用最小及缩窗步长 5,000。`min` 不再控制扩窗步长，这是升级后的行为变化；上下限、初始值仍可配置。
- 自动提交超时保持 0，只在读取到真实 COMMIT 后发送对应事务。达到最大窗口不会跳过剩余日志，而是继续分轮读取。
- 移除临时计时和统计日志以及额外 COUNT 查询，不改变必要错误、告警与指标。

## 已观察结果

此前在测试库验证单次 `INSERT INTO ... SELECT ...` 影响 3,468 行时，Sink 接收条数为 3,468。核对其他场景时应比较本次操作前后的接收条数增量，而不是将跨多次操作的累计计数与单次影响行数比较。

测试操作为单事务插入 13,056 行。三个版本都已限制挖掘启动 SCN 范围。

| 版本 | 扫描轮数 | 首轮扫描开始至事务分发调用返回 |
|---|---:|---:|
| 每轮增加 1,000 | 14 | 约 50.1 秒 |
| 每轮增加 5,000 | 10 | 约 47.8 秒 |
| 倍增，上限 100,000 | 6 | 约 39.9 秒 |

三次 Sink 最终计数均为 13,056，maxCBH 均为 13,056。倍增轮次的实际跨度为 20,000 / 40,000 / 80,000 / 100,000 / 100,000 / 28,954；两个 100,000 窗口分别耗时约 9.83 秒、9.37 秒。

倍增测试在 19:23:38.165 读取到 COMMIT，19:23:38.447 Sink 收到首条，19:23:41.319 Sink 接收计数达到 13,056。扫描阶段是本次主要等待位置。

这些是不同轮次的观察值，不是受控重复基准。数据库缓存、日志文件状态及负载可能不同；约 20% 的相对改善不能外推为生产承诺。计时不包含业务提交至首轮扫描之前的等待，分发返回不等于下游持久化成功。计数和最大编码不能证明事件逐条唯一、完整或字段正确。SQL 范围与窗口单元测试不能替代真实数据库验证。

## 主要风险

### 配置与验证边界

正数自动提交超时从连接器最后一次读取该事务 DML 时计算，无法证明数据库已经提交。超时发送的变更在数据库随后回滚时无法撤回；要求只同步已提交数据时，应将 `debezium.source.transaction.auto.commit.timeout.ms` 保持为 `0`。

严格等待 COMMIT 时，长事务会占用缓冲内存，并可能阻止恢复位点前进。若 LogMiner 未返回 COMMIT，事务会继续等待；数据库日志保留时间应覆盖事务持续时间、消费延迟及恢复窗口。将 `log.mining.transaction.retention.hours` 设为正数可能主动丢弃长事务，造成变更缺失。

较大扫描窗口可能增加单轮耗时和数据库资源消耗，须按实际环境验证。Checkpoint 成功不能单独证明 CDC 已追到某个事务；条数与最大编码不能证明逐条唯一性，单元测试也不能代替数据库验证。回滚、重启恢复和更大事务仍需按实际环境验收。

### 风险清单

| 风险 | 当前边界与影响 | 上线前控制或验证 |
|---|---|---|
| 全表大事务内存 | DML 跨轮缓存在 JVM 内存，窗口上限不是事务容量上限；大字段或多个并发事务可能导致 GC 压力、OOM、重启重放 | 用实际最大行数、字段大小和并发量压测，记录堆峰值及 GC；业务允许时分批提交，否则须评估磁盘缓冲等后续方案 |
| 未提交事务长期挂起 | 严格模式不会超时输出，缓冲可能长期占用内存，恢复位点可能滞后；缺失 COMMIT 时持续等待 | 测试长期挂起及随后 COMMIT / ROLLBACK，监控活动事务、缓冲与恢复位点 |
| 超时与保留配置导致一致性问题 | 正数自动提交超时可能发送未提交数据；正数事务保留期限可能主动丢弃长事务 | 要求仅提交数据时保持超时 0；不要将丢弃长事务作为无损释放内存手段 |
| 数据库开销与延迟 | 倍增减少轮次，但大窗口增加单轮挖掘和查询成本；SCN 跨度不是记录数或内存量，同一上限在不同负载下成本不同 | 测试正常小事务延迟和并发业务影响，监测数据库 CPU、IO、挖掘耗时；保守设置 max，不盲目放大 |
| 日志保留不足 | 长事务与积压需要历史日志；清理早于消费或恢复所需位置可能造成不可恢复缺口 | 日志保留覆盖最大事务时间、消费延迟及恢复窗口，验证轮转、归档切换和日志缺失时的行为 |
| 边界与版本兼容 | STARTSCN / ENDSCN 已用于本测试库；其他 DM 版本、同 SCN 多条日志、跨窗口 SQL 续片及跨文件事务尚未全面验证 | 在目标 DM 版本覆盖窗口边界、续片、大字段、归档切换及 DDL 混合场景 |
| 重启与交付语义 | 内存缓冲与恢复位点、Flink Checkpoint、Sink 提交之间的一致性尚未故障验证；不能承诺端到端恰好一次 | 在提交前、分发中、Checkpoint 前后故障重启，逐条比对；Sink 设计幂等或去重并验证 |
| 长时间运行 | 本次测试不能证明持续写入时能稳定追平，也不能证明全表修改的延迟可接受 | 进行持续负载和突发积压测试，记录吞吐、最老未完成事务、内存与恢复耗时 |

## 验收建议

1. 日常小事务与原版对照，多次测量从业务提交到 Sink 持久化的延迟，确认倍增策略不造成不可接受的常态退化。
2. 以生产最大预期事务做全表 INSERT / UPDATE / DELETE 测试，包括大字段与并发事务；不要用 13,056 行结果推定百万行安全。
3. 验证未提交不输出、完整及部分回滚、跨窗口和跨日志文件事务；使用稳定主键和预期事件集合检查缺失、重复及字段值，而非只比较最大编码。
4. 验证崩溃恢复、Checkpoint 恢复、Sink 故障、归档清理；明确日志保留、容量、恢复时间与允许的交付语义。

## 回退与后续

若数据库负载不可接受，可先降低 max 并同步调整 default/min，保持 `0 < min <= default <= max`。需要固定窗口时可将三者设为相同值；这会失去动态追赶收益，不能解决事务缓存内存问题。没有独立的增长策略开关，恢复线性增长需要回退该代码变更并重新构建。

不建议通过启用超时自动提交换取低延迟或释放内存。磁盘事务缓存、按耗时反馈调窗、会话复用及生产容量验收不在本次实现范围内，应在实测表明必要后单独评审。
